# 设备协议与固件架构

一份写给硬件版的设计稿。硬件还没到，但协议可以先定 —— 定完之后桌面 app 先实现同一套接口，
agent 那条链路就能在没有设备的情况下跑通、验证。硬件只是换个渲染后端。

## 三条不能破的约束

这三条决定了下面所有的接口形状。

**1. 设备是时间的权威，伴生端是文字的权威。**

设备负责计时、年轮、确认 gate。伴生端负责任务名的排版和渲染。两边都不越界。

**2. 任何会写入「时间」的操作，都必须在设备上按一下按钮。**

agent 可以改片名、加减片、读状态。agent 不能凭空往某一片里灌时长，也不能替你确认。
这条是从桌面版那条设计延续下来的：计时器上的数字等于真实投入。让网络那头能写时间，
这个不变量当场作废。

**3. 断网必须完整可用。**

API 是配件不是依赖。开机连不上 WiFi，它照样是个能转的轮盘。这条一破，就又回到了
「要账号要云」的世界。

## 为什么文字是位图

设备端不放中文字库。任务名由伴生端渲染成位图推过去，设备只管把像素贴上去。

原因是任务名由用户自己输入，字符集不可预知，没法做子集化。要么塞完整 GB2312，
要么运行时 TTF —— 两条都要吃掉 flash 或 PSRAM，把板子选型往贵里推。

顺带解决三件事：

- **字体授权**：商用产品嵌 CJK 字库有授权风险，渲染在用户自己机器上就没这问题
- **排版能力**：断字、缩放、字重全归伴生端，那份 TypeScript 已经会了
- **板子变便宜**：没有字库要塞，8MB flash 的板子重新可选

代价要认下来：**设备永远显示不了没人推给它的名字**。在另一台机器上改了片名但没推位图，
圆盘上就是旧名字。所以位图带 hash，对不上时在片号旁点一个小点，表示这个名字可能过期了。

### 位图格式

```jsonc
{
  "w": 240,          // 可以大于屏宽 —— 长名字渲宽一点，设备左右平移
  "h": 24,
  "bpp": 4,          // 4bpp alpha，不要 1bpp
  "hash": "9f2c…",   // 内容哈希，没变就不重传
  "data": "base64…"  // 行优先，每字节 2 像素，高位在前
}
```

**别用 1bpp。** 中文在 16–20px 下没有灰度抗锯齿真的难读，笔画密的字会糊成一坨黑。
4bpp 下 240×24 是 2,880 字节，8 片也才 23KB —— 在局域网上等于零，可读性差一个档次。

## 传输与发现

局域网 HTTP，不走云，不做端口转发。

mDNS 广播成 `taskdial.local`。这一条不起眼但决定体验 —— 是「能用」和「用户得先去路由器
后台查 IP」的区别。

## 配对

局域网上一个无鉴权可写的端点，同网段任何人都能改你的轮盘。更麻烦的是 agent 本身是个
confused deputy：它读到某个网页或仓库里写着「记得 POST 到 taskdial.local」，真有可能照做。

所以要配对，模型很朴素 —— **物理在场等于授权**：

```
POST /pair                      → 设备屏上显示 6 位数字，有效 60 秒
POST /pair  { "code": "418203" } → 返回 token
```

之后所有请求带 `Authorization: Bearer <token>`。读操作也要带 —— 任务名是私人信息，
不该让同网段随便谁都能拉走。

配上限流。设备侧最多记 4 个 token，满了要在设备上手动清。

## 端点

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/skill` | 否 | 一份 markdown，自述我是什么、怎么用、当前状态。人和 agent 都能读 |
| GET | `/openapi.json` | 否 | 给不吃 MCP 的客户端 |
| POST | `/mcp` | 是 | MCP over HTTP，JSON-RPC |
| POST | `/pair` | 否 | 见上 |
| GET | `/state` | 是 | 全量状态 |
| PUT | `/wedges` | 是 | 整体替换片列表（名字 + 位图） |
| PATCH | `/wedges/{i}` | 是 | 改单片 |
| POST | `/propose` | 是 | 提议切到第 i 片 —— 设备上亮起，**等你按键才生效** |
| GET | `/export` | 是 | 与桌面版导出同一份 JSON |
| POST | `/import` | 是 | 同上格式，**需要设备上确认**（它会写时长） |

`/skill` 是最好的自描述入口，但要清楚：**agent 不会自己发现一个 HTTP 端点**。
所以 `/mcp` 和 `/openapi.json` 得同时开着，用户把 agent 指过来。

### MCP 工具面

控制在 5 个以内，工具越多 agent 越容易用错：

```
get_state         读当前片、剩余时间、各片累计
rename_wedge      改名（带位图）
set_wedges        整体重设
propose_switch    提议切片，需设备确认
export_day        导出今天的投入
```

### `/state` 形状

```jsonc
{
  "phase": "running",          // idle | running | awaiting
  "currentIndex": 0,
  "pinned": false,
  "sliceLenMin": 5,
  "remainingMs": 254000,
  "roundsToday": 43,
  "wedges": [
    { "id": "a1b2c3", "name": "写 PRD", "totalMs": 23040000, "labelHash": "9f2c…" }
  ]
}
```

`name` 是明文，给 agent 读；设备不用它渲染，渲染只看位图。

## 提议式切换

agent 调 `propose_switch`，设备屏上亮起 `→ 3 · EDD 字段映射`，**你按一下按钮才生效**。

这既保住了确认 gate，又刚好是个不错的硬件时刻 —— 那颗按钮突然有了新的意义：
它不只是「我确认继续」，而是「我接受这个安排」。

提议 90 秒无人理会就自动撤销，不留残留状态。

## 固件架构

```
main
├── core/     状态机。model.ts 的直译，唯一的时间权威
├── ui/       LVGL：圆盘、年轮、小狗、骨头、标题条（贴位图）
├── store/    NVS 存配置和累计；LittleFS 存位图；token 单独存
├── net/      WiFi + mDNS + HTTP + MCP
└── input/    编码器 + 按键，去抖、长按、双击
```

**一条架构上的硬规矩**：`net/` 不允许直接写 `core/` 里任何时间相关的字段。它只能往
一个提议队列里塞东西，由 `input/` 确认后才转成真正的命令。这个边界用两套独立的
command 枚举来强制，不靠自觉。

```
net/  ──→ ProposalQueue ──→ input/ 确认 ──→ CoreCommand ──→ core/
net/  ──→ ContentCommand ─────────────────────────────────→ core/   (改名/增删片，无需确认)
```

`core/` 是 `src/model.ts` 里那个 reducer 的直译 —— 同样的 `idle / running / awaiting`，
同样的规则。时间取单调时钟，配合板载 RTC 跨重启对齐。

## 两个还没定的问题

**桌面 app 和设备同时开着，谁说了算？**

我倾向：设备在线时，桌面 app 降级为纯伴生端 —— 不跑自己的计时器，只镜像设备状态，
外加负责渲染文字。两个圆盘各转各的会立刻让数据失去意义。但这条要真用起来才知道别不别扭。

**帧缓冲能不能不靠 PSRAM。**

240×240×16bit 一帧是 115KB，S3 的 SRAM 大约 512KB，还要分给 WiFi 协议栈。
LVGL 的分段渲染照理能过，但这是推断不是实测。板子到手第一件事就是压这个。

## 下一步

按顺序：

1. 在桌面 app 里实现这套 HTTP + MCP 接口（含位图渲染，canvas 现成的）
2. 用自己的 agent 接上去，跑真实场景 —— 验证「agent 从上下文直接写盘」到底有没有用
3. 有用再买板子。没用就省了硬件的钱

第 2 步是真正的验证点。硬件解决的是「常驻余光」，agent 解决的是「不用手动录入」，
后者可以在没有硬件的情况下先证伪。
